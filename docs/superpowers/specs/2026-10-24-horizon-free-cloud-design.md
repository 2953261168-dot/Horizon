# Horizon 免费云端运行方案（待确认，尚未部署）

## 用户要求
日报每日自动生成、更新网站并发邮件，不依赖用户电脑、Edge 或 Codex 常开；只接受免费方案。不能再靠用户发现缺报后手动恢复。现有网站与当天已发邮件保留，迁移期间不重复发信。

## 选择与边界
以下平台组合是助手根据现有 Python 项目作出的技术选择，尚待用户确认。

1. **独立公共 GitHub 执行仓库**，建议名 `horizon-runner`，不创建为 fork。使用标准 Ubuntu 执行器，运行现有 Python 采集、生成、发布和发信。原 Horizon 仓库继续保存源码和网站，避免同时改版网站。现有 fork 不再承担定时计算。
2. **Cloudflare Workers Free** 做独立时钟和有界恢复：读取当天状态，必要时通过 GitHub API 启动执行任务。它不运行长时间 Python 生成，也不保存邮件或新闻正文。
3. **Healthchecks.io 免费检查**做独立的缺报提醒。只有当天网站部署及 SMTP 接受都成功才向检查地址报到；未收到报到时，由该服务向用户的已验证邮箱发故障提醒。不能把同一个 GitHub 工作流内的报警当作独立监控。

免费服务没有准点 SLA。GitHub 全平台不可用时，本方案不能在别处立即生成，但必须发出独立缺报提醒，不能假装成功；新独立仓库仍须遵守 Actions 用量和服务政策。

## 免费条件（2026-10-24 官方资料已核对）
- GitHub 公共仓库的标准托管执行器运行分钟免费；不使用大规格执行器。产物短期保留，限制缓存与存储，不开付费额度。
- Workers Free 每日100,000请求、每次10ms CPU额度。该 Worker 只发少量 API 请求并处理小状态对象，目标每日少于200次检查；实测超过免费限制即缩小处理量，不升级套餐。
- Healthchecks.io 免费20个检查、不要求信用卡，本方案只需1个。
- 不使用免费试用后自动收费的实例，不开 Workers Paid、付费数据库或付费执行器。若免费条件不适用，停止开通并说明。

资料：[GitHub Actions计费](https://docs.github.com/en/billing/concepts/product-billing/github-actions)、[Workers计费](https://developers.cloudflare.com/workers/platform/pricing/)、[Cron Triggers](https://developers.cloudflare.com/workers/configuration/cron-triggers/)、[Healthchecks.io](https://healthchecks.io/)。Cloudflare时钟使用UTC，调度变更可能需最多15分钟生效。

## 正常运行与恢复
- 北京时间06:00开始准备，目标08:00发送。原来08:00的目标沿用，提前准备留出模型和抓取耗时。
- GitHub定时器与Cloudflare独立时钟均可触发，但执行前检查当日期次状态、运行中的任务和互斥锁，不能并行生成同一期。
- 尚未准备、任务未启动或明确失败时，有界补跑；建议最多3次生成尝试。一直运行中的任务不重复启动，超时后明确标记失败。
- 发布前核对必要正文、原始出处、当天日期及内容数量。建议20篇选题至少18篇有效才发布；不足20篇选题时按实际选中数量验收，不凑稿。少量因提供商拒绝而省略的稿件必须写入机器记录。
- 以期次完成记录及内容哈希判断准备完成，替代“文件存在且非空”。网站部署到对应提交成功后，才能把本期标记为可发。
- 08:00后发送当天已验收版本；发现明确未发送才重试。沿用原仓库 `horizon-mail-state` 的发送记录，保留今天的sent标记，迁移不重复发送。
- SMTP结果不确定时保留sending保护并报警，不盲目重发。服务器接受仅代表发信成功，不能宣称用户收件箱已到账。
- Healthchecks建议08:00报到时间、30分钟宽限期，故障恢复后发送恢复通知。首次配置后，以今天已经核实的真实SMTP发送记录初始化，避免检查一直停留在New而无法发现首次缺报；不能用测试冒充生产成功。具体邮箱由用户在服务界面验证，密码和密钥不进聊天。

## 最小权限与一次性设置
- 用户需要一次性登录/注册Cloudflare和Healthchecks免费账号，并完成条款、验证码与邮箱验证。这些步骤由用户亲自完成。
- 新执行仓库需要重新录入模型密钥、SMTP授权码和收件地址；GitHub旧Secrets不能读回。用户直接在Secrets界面填写，不发给助手。
- 发布/状态写入凭证仅授权原Horizon仓库所需内容权限；Cloudflare触发凭证仅授权新执行库的Actions权限，程序只调用固定的指定工作流。GitHub令牌的权限边界是所选仓库，不能宣称令牌本身可限制到单个工作流。不得使用全账号通用令牌。
- 访问令牌创建与授权步骤由用户在具体界面完成。日志不输出令牌、密码、收件地址或监控报到地址。
- 不自动覆盖用户手动禁用的工作流。若服务被停用或凭证失效，记录原因并发独立缺报提醒；不绕过平台限制。
- Worker通过固定公开地址只读获取原Horizon仓库的期次状态；通过新执行库的Actions读写凭证查询运行状态和触发指定流程。不把原库的写入凭证交给Worker。
- 公共状态记录只包含日期、阶段、运行ID、尝试次数、时间戳、正文数量和公开产物哈希；不包含收件地址、原始SMTP日志、邮件正文、密钥、监控报到地址或未经清理的异常全文。缺失、格式错误或无法读取的状态不得被当作成功。

## 切换与验收
1. 先完成部署文件、单元测试与只读检查，不动正在正常运行的旧生产流程。
2. 新执行库用不发信模式演练：正常运行、任务未触发、模型输出失败、发布失败、重复触发、超时、错误期次与凭证失效。
3. 先验证Cloudflare真实自动触发新执行库，再验证新库能复用发送记录、不会重发今天的邮件；不再发送额外样刊。
4. 验证Healthchecks在未报到时确实提醒、恢复后确实恢复；使用独立测试检查，不能发送伪造的日报成功报到。
5. 全部通过后，经用户确认切换：停用原仓库自动生成及发信，保留Pages部署；启用新执行库及Cloudflare调度。不得同时留两个生产发信入口。
   切换的阻断条件是旧流程仍有运行中/排队的生成或发信任务，或存在未核实的sending记录。先停止新增触发、等待旧任务结束，不取消进行中的SMTP发送；状态不确定时暂停切换并报警，只有人工核对SMTP结果并明确确认后才能修正记录。今天已有核实的sent记录，可在无活动任务时演练切换，不重发今天邮件。
6. 核对一次真实次日自动周期的文章、网站部署、SMTP日志和缺报检查，才报告每日自动链路已验证；不能拿手动运行替代。
